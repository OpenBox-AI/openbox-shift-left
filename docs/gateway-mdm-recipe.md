# Hardening the local gateway with MDM

OpenBox ships **artifacts and a recipe**. It does not operate an MDM, build MDM
profiles, or manage your fleet; that boundary is deliberate, and it is why this
page is a recipe rather than a feature.

Read
[`docs/architecture.md`](architecture.md#assurance)
first for what the evidence proves generally. This page covers one question:
what changes when you push the gateway's configuration from your MDM instead of
letting each developer own it.

## What you are buying, stated honestly

**Nothing here makes bypass impossible.** It makes bypass require privilege the
developer does not routinely have, and it keeps every bypass visible.

| | Base tier | MDM tier |
|---|---|---|
| Who owns the config | the developer | root |
| Developer can edit it | yes | no, not without escalating |
| A shell `export ANTHROPIC_BASE_URL=…` still wins | yes | **yes** |
| Bypass detectable in stored data | yes | yes |
| Bypass *prevented* | no | no |

That third row is the one people miss. A root-owned settings file stops a
developer rewriting the file; it does not stop them setting an environment
variable in the shell they launch the tool from. **Closing that needs egress
control**, which is yours to deploy; see below.

`openbox doctor` reads the tier from **file ownership**, not from a flag OpenBox
writes. There is nothing to configure and nothing to claim: it stats the file
and reports what it finds. A file at the managed path that is *not* root-owned
is reported as base tier, with the reason.

## 1. What to push

Two files, identical in content to what a developer install writes. Only the
ownership differs.

### Managed settings

Push to the provider's managed-settings path:

| OS | Path |
|---|---|
| macOS | `/Library/Application Support/ClaudeCode/managed-settings.json` |
| Linux | `/etc/claude-code/managed-settings.json` |
| Windows | `C:\Program Files\ClaudeCode\managed-settings.json` (the older `ProgramData` path is no longer read) |

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:8788"
  }
}
```

Owned by `root`, mode `0644`. Managed settings take precedence over
`~/.claude/settings.json`, so this is the value the tool reads.

If your org already pushes a managed-settings file, **merge the `env` key**
rather than replacing the file. OpenBox's own writer preserves foreign keys; an
MDM payload that replaces the whole file will not.

### The service unit

**Status:** the unit content below is generated by OpenBox
(`internal/cli/gatewayservice`) and is what a developer-scope install will
write. Wiring it into `openbox init` is not done yet, so today you copy the
content from here rather than running a command to emit it. That is a gap in the
installer, not in the artifacts; the bytes are the bytes.

MacOS; `/Library/LaunchDaemons/ai.openbox.gateway.plist`, owned by `root:wheel`,
mode `0644`. This is the exact content OpenBox generates; adjust the binary
path:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>ai.openbox.gateway</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/openbox</string>
    <string>gateway</string>
    <string>--addr</string>
    <string>127.0.0.1:8788</string>
    <string>--upstream</string>
    <string>https://api.anthropic.com</string>
    <string>--shutdown-grace</string>
    <string>30s</string>
  </array>
  <key>KeepAlive</key>
  <true/>
  <key>RunAtLoad</key>
  <true/>
  <key>ExitTimeOut</key>
  <integer>30</integer>
</dict>
</plist>
```

Linux; a system unit at `/etc/systemd/system/openbox-gateway.service`, then
`systemctl enable --now openbox-gateway`:

```ini
[Unit]
Description=OpenBox local gateway (model-call governance)
After=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/openbox gateway --addr 127.0.0.1:8788 --upstream https://api.anthropic.com --shutdown-grace 30s
Restart=always
RestartSec=2
TimeoutStopSec=30

[Install]
WantedBy=default.target
```

The developer-scope equivalents (a launchd **agent** under
`~/Library/LaunchAgents/`, a systemd **user** unit under
`~/.config/systemd/user/`) carry identical content; that sameness is the point:
the MDM tier is the same bytes with different ownership, which is exactly what
`doctor` reads the tier from.

Note the flags: `--addr`, `--upstream`, `--shutdown-grace`. There is **no
`--config`** flag; a unit invoking one would be rejected by flag parsing and the
gateway would fail to start on every boot.

**The stop timeout must match the gateway's `--shutdown-grace`** (default 30s).
`http.Server.Shutdown` never force-closes an active connection, so whatever is
still streaming when the grace expires is cut when the process exits. Set the
supervisor's timeout shorter and it SIGKILLs before the grace is ever used; set
it longer and you gain nothing. Launchd defaults to 20s and systemd to 90s, so
launchd's needs raising explicitly.

## 2. Egress control; the part that actually prevents

This is what closes the shell-export hole, and it is the only item on this page
that prevents rather than detects.

The shape: deny outbound traffic to the provider's API from everything except
the gateway process, on the developer's machine or at your network edge.

```
# Illustrative only; express this in whatever your fleet already uses.
# ALLOW  <gateway binary / its uid>  ->  api.anthropic.com:443
# DENY   everything else             ->  api.anthropic.com:443
```

Two honest cautions:

- **This can break the developer's machine** in ways OpenBox cannot see or
  explain. A rule that also blocks the gateway makes every model call fail, and
  the developer will experience that as "the tool is down".
- **Verify it, do not assume it.** A rule scoped by process name is trivially
  defeated; one scoped by uid or by a signed binary identity is not. If you
  cannot verify which of those you deployed, you are on the detection tier with
  extra steps.

## 3. Verify what you deployed

On a managed machine:

```bash
openbox doctor
```

Under the `Local gateway` heading you should see `tier mdm` and `owned by root`.
If you see `tier base` with a note about ownership, the payload landed but the
ownership did not; which is the case that looks like success and is not.

Then confirm governance is actually happening rather than merely configured. The
query for that changed, and the old one no longer works: "model turns with **no
gateway spans**" is now true of every session, because a developer session stores
no span rows at all -- and it was already vacuous before the spans were removed,
since core never persisted them on this path.

What still distinguishes a relayed call from one the relay never saw is the
**`activity_id` namespace**. A relayed call's rows carry `:gateway:` or `:proxy:`
in their `activity_id`; a hook-derived turn carries `<session>:turn:<n>`. So:

```sql
-- Model calls the relay never saw: turns exist, no in-path lane observed any.
select run_id,
       count(*) filter (where activity_id like '%:turn:%')    as hook_turns,
       count(*) filter (where activity_id like '%:gateway:%'
                          or activity_id like '%:proxy:%')    as relayed
from governance_events
where activity_type = 'llm_completion'
group by run_id
having count(*) filter (where activity_id like '%:gateway:%'
                          or activity_id like '%:proxy:%') = 0
   and count(*) filter (where activity_id like '%:turn:%') > 0;
```

Two cautions. A session governed by the **telemetry** lane legitimately has no
in-path rows, so exclude `:otel:` sessions or you will read a configuration choice
as a bypass. And `openbox doctor` now reports the local half of this directly: a
lane whose unit is installed and listening while its managed env keys have gone
missing from the settings file, which is what un-routing looks like from the
machine rather than from the database.

## What OpenBox will not do

- Build or ship MDM profiles, agents, or fleet tooling. Owning prevention
  through the back door is still owning prevention.
- Tell you a configuration is bypass-proof. None of them is.
- Operate anything. The gateway runs on the developer's machine; there is no
  org-operated OpenBox service in this architecture.
