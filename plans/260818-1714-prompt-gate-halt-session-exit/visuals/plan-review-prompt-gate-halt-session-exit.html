02 Shape of the change

Two mechanisms, one shared engine. Neither adds a table, an endpoint or a service — which is why That decision extends that decision rather than competing with it.

Mechanism A — the prompt gate

UserPromptSubmit becomes synchronous. The PromptSubmitted event is evaluated by /evaluate before the prompt is processed, through the same hookflow.EnforceGate as a tool call: same escalation, same failure policy, same approval hold, same spool dedupe.

What differs is only two seams — promptTarget (how the event reads) and promptOutputContract (how a refusal is spelled). 75 lines and 50 lines respectively.

Mechanism B — HALT ends the session

A HALT the control plane actually returns emits continue:false + stopReason (the turn stops now) and writes a per-session latch. Every later gated hook in that session refuses locally — resume included — with zero round-trips.

BLOCK still refuses one call. That distinction is the whole point: the developer runtime previously mapped both to one permissionDecision:"deny", and the model routed around the strongest verdict governance can issue.

03 The two gaps it closes

Both were observed live, not theorised — the diagnosis is debug-260818-1656-halt-block-does-not-stop-loop.md.

Gap 1 — only tool calls gated

PromptSubmitted carries the developer's intent — the thing every later alignment check is scored against. It was observe-only. A policy that wanted to stop work at the prompt could only watch it happen post-hoc in the dashboard.

Gap 2 — HALT was indistinguishable from BLOCK

The reference SDK terminates the workflow on HALT (GovernanceHaltError). The developer runtime mapped HALT and BLOCK to one per-call deny — and Claude Code reads a deny as “this call refused, keep going.” Nothing ever emitted the documented session-stop lever.

Why this is a decision record and not a patch

HALT and BLOCK now mean different things on the developer runtime, which gives policy authors the same escalation ladder the agent runtime already had. That is a semantics change to a governance contract, so it is recorded — that decision, accepted 2026-08-18, 80 lines, no new table/endpoint/service.

04 The kill discriminator

This is the part the plan itself flags as “must be exact,” and it is where a plan review earns its keep. The condition is four terms, and the position in the sequence is load-bearing. 

// adapters/common/hookflow/gate.go — marked AFTER the approval hold resolves
if dec.Evaluation.Verdict == client.VerdictHalt
   && dec.Source == SourceEvaluate
   && !dec.FailOpen {
    dec.SessionHalt = true
}

Four things are excluded by construction, not by a list of special cases:

fail-closed synthesized HALT

Carries FailOpen=true. A transient outage must never permanently kill a session. Pinned by C31.

approver REJECT

Re-sourced approval:decided. A human refused this call — that is a deny, not a session kill.

unanswered hold — the regression

ApprovalUndecided mutates verdict → HALT. It previously left Source=evaluate, so every hold timeout would have killed the session. Hence the new approval:undecided source.

latch replay

session-halt source, so the enforcement audit can tell “the server said HALT” from “this session was already halted.”

The ordering constraint, stated plainly

ApplyFailurePolicy runs after the evaluation, and SessionHalt is marked after the approval hold. Move either and the failure mode is not a wrong log line — it is a fail-closed org denying every gated call without ever asking (that decision lesson C1 caught), or every approval timeout terminating a session. Both directions are pinned by tests, and both tests pass.

The gate sequence

  1. Gated hook fires — PreToolUse or UserPromptSubmit
    gated := ResolveEnforce() && (PreToolUse || UserPromptSubmit) — hookrun.go:202
  2. Is the session already latched?
    yes Replay from the latch, render continue:false + refusal. Zero round-trips — the observe copy is still spooled.
    no Continue down the gate.
  3. Local step — redacts, never decides
    Secret detection only. That decision removed its verdict; it returns “no verdict” by design.
  4. POST /evaluate — unconditional for every gated call
    No local narrowing. Risk is a property of the policy, not of the engine.
  5. ApplyFailurePolicy — strictly after the evaluation
    Ordering is load-bearing. Placed earlier, a fail-closed org synthesizes a HALT before asking, reads as “already tightened,” and denies every gated call without ever making a request. Conformance case C1 caught exactly that.
  6. Approval hold — only if the server asked
    Re-sources the decision to approval:decided or approval:undecided. A degraded evaluation filed no record, so it is never held for.
  7. Mark SessionHalt — and only here
    HALT && Source==evaluate && !FailOpen. After the hold, so no hold outcome can qualify — which is what stops every approval timeout from killing a session.
  8. ApplyDecision — downgrades halt to deny unless SessionHalt
    One choke point. Every synthesized HALT loses its session-stop here rather than in four separate call sites.
  9. Was a halt actually emitted?
    yes Write the latch — the session is over, resume included.
    no Per-call deny, block or proceed. No latch.

05 Latch lifecycle

The latch is the durable half of “cannot continue.” The provider's strongest in-contract response stops only the current turn, so a session that must never do governed work again needs state that outlives the hook process — one small file per halted session, consulted first by every later gated hook.

The second half is what C27 asserts by counting /evaluate hits: a latched session makes zero.

Four design choices worth not re-litigating

Collision safety is deliberate, not incidental

The filename pairs the sanitized session id (legible in a directory listing) with a sha256[:4] of the raw id. Two ids that sanitize alike therefore cannot share a latch — a collision would halt an innocent session. Pinned by TestSessionHaltNoCollisionAcrossSanitizedIDs and TestSessionHaltPathIsConfinedToHaltDir.

A corrupt latch still halts

Presence is the decided state; an unparseable file falls back to a generic reason rather than quietly un-halting a session the control plane terminated. The inverse default would make file corruption an enforcement bypass. TestSessionHaltCorruptLatchStillHalts.

The write is off the blocking path

The halting response is already on stdout when WriteSessionHalt runs, so a write fault costs only the later calls' local refusal — they fall back to a fresh evaluation. Logged loudly, never surfaced (INV-3). An empty session id never latches at all.

It is a faithful-client mechanism, not tamper-proof

Deleting the file un-halts the machine's view. That is consistent with that decision threat model — everything client-side here is readable and writable by the developer, including the signing key — and the server-side record still shows every verdict. That decision says so in as many words; the docs must keep saying it.

08 Drift & findings
F1 · correctness · found live, fixed post-merge

The plan's upgrade remedy was inert

The Registration section ends: “Existing installs need openbox init re-run (same as That decision hooks).” True as an instruction. False as a remedy — and the failure was silent in the worst direction.

writeLocalHooks decided ownership by matching the exact command string, then skipped any entry that already matched. So a registration shape change — which is precisely what this plan made, raising UserPromptSubmit's timeout from 5s to the 30s gating ceiling — never reached an existing install. Claude Code kept the 5s kill, killed the prompt gate mid-evaluation, and the gate failed open: no enforcement, no error, through the very command the docs name as the upgrade step.

Found on the first manual test after merge. Fixed in 8adacf6: re-init now reconciles the fields the installer owns (timeout, statusMessage) on our own entries — the rewake watcher included — and leaves foreign hooks untouched. Second-invocation shape is pinned idempotent by localhooks_stale_engine_test.go (+108 lines).

The transferable rule — and this repo already knows a version of it, from the duplicate-engine work: when a plan names a remedy, exercise the remedy in the state it is meant to repair. Fifteen green tests can all run init exactly once. The bug lives in the second invocation.

F2 · plan text over-specifies — code is equivalent

The plan writes the latch condition as res.Decision==DecisionHalt && res.Emitted; gate.go checks only the first conjunct. That is not drift: ApplyDecision returns a zero ApplyResult on every path that writes nothing, so Decision is non-empty only when Emitted is true. The second term was redundant. Verified by reading all four early-return paths.

F3 · discoverability — the C-series numbering is adapter-local

C27–C31 live in adapters/claude-code/enforce_conformance_test.go, not under contracts/. Since the plan, that decision and CLAUDE.md all cite “C…” numbers alongside contracts/dev-event conformance language, a reader who greps contracts/ for C27 finds nothing. Cosmetic, but it costs a newcomer a few minutes at exactly the moment they are trying to trust the evidence.

F4 · scope hygiene — PR #7 carried a second plan's documents

The merge diff (46 files, +2668/−83) includes nine files belonging to 260814-2235-dev-session-unauthored-halt-fix — its plan.md, five phase files and three research reports. Harmless docs, but anyone reading PR #7 as this plan's blast radius will overcount it by roughly a third, and the two plans are already easy to conflate because one is the pending upstream fix for the other's accepted consequence.

F5 · the pre-merge review was real, and one finding was a correctness bug

The trail (review-260818-1910) records 10 finder angles, 7 findings, all fixed and re-verified, plus a YAGNI audit that cut nothing. The one correctness item is worth naming because it shaped the shipped API: the latched-path diagnostic logged the hook name where every other enforce line logs the tool name.

The fix gave ReplaySessionHalt an explicit toolName parameter and documented the expectation in the signature's comment — so the next caller cannot repeat it by accident. Three efficiency claims were refuted with reasons, which is the right outcome to record.

Checked and found clean — six things a reviewer would reasonably suspect
  • Double findings surfacing on a gated prompt. The gated branch returns; the :304 block is unreachable for it. One stdout document per hook run.
  • Latch replay skipping observation. It doesn't — hookrun.go:210 spools the refused attempt and nudges the flush, so the dashboard shows what the latch did.
  • Codex accumulating latch state it never reads. Structurally impossible: its Render never returns the halt literal.
  • The prompt gate attaching content twice. It doesn't — promptTarget.DevEvent delegates to the same Mapper.Map the observe copy uses, so one event id and one capture gate.
  • Prompt path reintroducing an input-rewrite surface. ContentFieldKeys() returns nil and ToolInput() returns nil — the pair makes updatedInput structurally impossible on prompts.
  • The 30s registration drifting from the evaluator's ceiling. Both read the same preToolUseHookTimeoutSec const, and a test compares the JSON bundle against it directly.
09 Open risk register
R1
The accepted consequence is still live: core turns an operational failure into a session kill

“Every server HALT kills, authored or not” was an owner decision, taken over client-side verdict discrimination (already rejected by plan 260814-2235). The remedy is core-side — and it has not landed.

As of the 2026-08-20 verification report, core still returns VerdictHalt with reason “Session is no longer active” and no policy id for a non-pending session (internal/services/governance_workflow.go:240-253) — purely operational, indistinguishable at the client from a governance decision. Sibling plan status: pending, with phase-02 targeting core; no landed fix found on any local core branch.

Before that decision that defect denied calls until the record cleared. After it, it ends the session — and the latch means resume does not help. This is the single largest behaviour-change risk in the plan, it is documented, and it is not a bug in this repo.

Live owner-accepted blocked on openbox-core plan 260814-2235 pending

No end-to-end proof: testbed §A3 has never run

Everything proven so far is proven against a stub /evaluate. §A3 publishes a raw-rego halt through the real backend and asserts the turn stopped, the file was never written, the latch exists and replays are audited. Until it runs, the claim “a policy author can stop a session” is inferred from the client half only. Same status discipline as the That decision/0018 work — consistent, and still a gap.

R4
Residual mechanical limits, all documented
  • Parallel tool calls already past the gate when the HALT lands still run — it is a pre-execution gate; unavoidable.
  • The interactive REPL process stays open but inert; the hook protocol has no process-exit response (verified against the hooks reference). In headless -p the turn stop ends the run.
  • Prompt approvals are addressable only at session granularity, because activityPairKey carries no span for signal events. Every failure mode lands on block — over-ask, never over-grant.
  • No operator surface for the latch: no doctor listing, no unlatch command. Validated de-scope; enforcements.jsonl + the refusal reason + the documented file path are the whole surface.
  • statusMessage on UserPromptSubmit is assumed ignored-if-unknown on older Claude Code, by analogy with that decision hook-key probe. Not re-probed.
