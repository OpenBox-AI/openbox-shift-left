# Phase 4 — Validated report and OpenBox recommendations

**Status:** in progress — OS-04-01 through OS-04-03 implemented; OS-04-04 live qualification and human review remain

**Parent:** [Lean local OpenShell project security evaluation](plan.md)

## Goal

Turn one untrusted Phase 3 candidate into a self-contained, sealed security
report. Every accepted issue must remain grounded in the verified observation
pack. Every OpenBox recommendation must be generated by deterministic Phase 4
code from a separately captured, GET-only view of the target agent's current
control posture and a checked-in recommendation catalog.

The output remains advisory and sensitive. This phase adds no Apply, approval
decision, governed rerun, control publication, backend, Core, provider, image,
credential, or infrastructure change.

Phase 3 is intentionally issue-only: its candidate has no current-control,
capability, recommendation, enforcement, or verification authority. Phase 4
independently reverifies the observation and candidate before it reads target
posture. Candidate prose never supplies a target control, capability, action
identity, or executable constraint.

## Corrected Phase 4 decision

The earlier draft called `project finalize` offline while also requiring
recommendations for the target system's current controls and exact backend
tuple. Phase 2 deliberately removed the control crawl and exposes no backend
build/version identity through its dashboard API contract, so both claims
cannot be true.

Keep the three-flag command already printed by the Phase 3 skill, but make its
authority boundary explicit:

1. validate the observation and complete candidate offline and fail before any
   credential or network access;
2. use the existing host-side `OPENBOX_BACKEND_URL` and
   `OPENBOX_CONTROL_TOKEN` only for one bounded, local, GET-only target-posture
   capture;
3. map validated issues to inert suggestions using only that sealed posture and
   a checked-in recommendation catalog; and
4. seal a self-contained report pack. All later verification and rendering of
   that pack are offline.

Do not invent a backend build tuple. The recommendation catalog is bound to a
named read contract and its own digest, not to an unavailable server version.
A recommendation seam is observable only when the credential permission, safe
GET route, response shape, target agent, and organization all reconcile. This
proves the target exposes that read seam; it does not prove a recommendation
was applied, is effective, or can be automatically published.

An unavailable seam never suppresses an otherwise valid issue. Phase 4 records
the recommendation as unavailable, or emits an `sdk_integration` gap only when
the observation and coverage ledger support that conclusion. It does not
fabricate policy capability and does not reject the whole report merely because
one issue has no supported OpenBox mapping.

## Public interface

Add:

```text
openbox project finalize \
  --evaluation OBSERVATION_PACK \
  --analysis CANDIDATE_ANALYSIS_JSON \
  --output REPORT_PACK
```

All flags are required and positional arguments are rejected. The observation
pack and candidate must already exist as owner-readable regular files/directories.
The output path must not exist. Publication uses a mode-0700 same-parent staging
directory, mode-0600 files, a manifest-last atomic rename, and no replacement.

The target agent and organization come only from the verified observation pack;
there is no agent, organization, endpoint, credential, capability, control,
model, host, or Apply flag. The local backend URL and existing control token use
the same fixed host-side configuration as `project evaluate`; neither enters the
report. `finalize` invokes no model, host skill, project image, OpenShell run, or
OpenBox write route.

Before the first backend request, `finalize` must:

- securely open and independently verify the complete
  `ai.openbox.project-observation/v1` pack;
- open the candidate without following links, enforce mode/owner/type and the
  4 MiB bound, reject duplicate keys and trailing data, validate the public
  schema, and require the exact Phase 3 skill and standards identities;
- require the candidate observation digest, evidence references, standards,
  result shape, ordering, coverage, and authority roles to reconcile with the
  verified pack; and
- resolve the new output target and prove it is absent.

Any failure stops without network access and without creating the output. After
successful offline validation, any posture-capture, mapping, projection, or
publication failure removes only the exact staging directory and leaves the
requested output absent.

On success print only:

```text
project security report sealed: REPORT_PACK
  pack_digest: sha256:<digest>
```

Extend `openbox project verify PACK` by discriminator without changing the
historical audit-pack or Phase 2 observation success/error bytes. A valid report
prints exactly:

```text
project security report verified: ai.openbox.project-security-report/v1
  pack_digest: sha256:<digest>
```

Extend `project report --pack` by report-pack schema. It independently verifies
the report pack and then emits its checked Markdown, JSON, or SARIF projection.
Existing audit-pack report/proposal bytes remain frozen. `project propose`
remains historical-only.

## Authoritative candidate validation

The Phase 4 validator is the first public authority for a Phase 3 candidate. It
may reuse the immutable Phase 2 observation reader and public schema/catalog
bytes, but it must not trust the Phase 3 qualification oracle or a prior
`project verify` result.

For each result:

- `issues` requires 1–100 fully valid issues. Phase 4 assigns deterministic
  report issue IDs from normalized validated content and preserves candidate
  IDs only as provenance.
- `no_supported_issue` requires zero issues and produces zero recommendations.
  The report states that the bounded observation supports no catalog issue; it
  is not a security pass.
- `inconclusive` requires zero issues, names the relevant non-observed coverage
  gaps, produces zero control recommendations, and is never rendered as a pass.

Reject the complete candidate on forged, unknown, duplicate, unsorted,
cross-run, wrong-authority, or unresolved evidence; an unknown standard or
coverage gap; an observed coverage entry cited as a limitation; a mismatched
pack, skill, catalog, or bundle identity; unsupported effect or behavior order;
unsafe strings; secret material; or any candidate-carried recommendation,
control, capability, enforcement, severity, verification recipe, endpoint,
credential, command, patch, Apply, or approval field.

## Target-posture capture and recommendation catalog

Define `ai.openbox.project-target-posture/v1`. Capture it only after the full
offline gate passes. The first local contract is
`local-dashboard-control-read/v1` and permits only bounded `GET` requests for:

- `/auth/profile`;
- the exact observation agent identity;
- every paginated current guardrail;
- every paginated current policy plus the current-policy pointer; and
- every paginated current behavior rule plus the returned aggregate rule-set
  hash. The collector does not call a `behavior-rule/current` route.

Use the existing exact local URL, request deadlines, page and byte bounds,
disabled proxies/redirects/cookies/compression, credential placement, and
credential-field rejection posture from Phase 2. Require the observation's
agent and organization, the established read permissions, known response
envelopes, complete pagination, and identical second-pass control identities
and versions. Any non-GET request, drift, ambiguous identity, unknown envelope,
unsafe field, or missing required read seam stops report creation.

The sealed posture contains only safe canonical projections needed for
mapping: target identity, read-contract identity, catalog identity, capture
window, control IDs/types/statuses/stages or action classes, update/version
identities, and explicit unavailable or opaque seams. It excludes credentials,
headers, raw Rego, write routes, executable payloads, free-form control bodies,
and arbitrary backend responses. Unknown control semantics are `opaque`, not
silently discarded or interpreted.

Add one closed `ai.openbox.project-recommendation-catalog/v1` resource. Freeze
its MVP version and digest in the implementation task. For each inert
recommendation kind—`behavior_rule`, `policy`, `guardrail`,
`approval_requirement`, and `sdk_integration`—the catalog defines:

- eligible evidence-derived action classes and issue/standard mappings;
- the read permission, safe route, and response projection that establish the
  target seam;
- closed non-executable constraint vocabulary;
- which current-control identities may be cited for review; and
- the limitations that prevent an enforcement or Apply claim.

The catalog contains no write endpoint, request payload, credential, command,
patch, or publication recipe. Updating it changes its digest and requires full
mapping and report requalification.

## Deterministic recommendation mapping

Map only normalized issues accepted by the authoritative validator. Derive the
target agent, action class/name, and ordering from cited retained backend
records—not candidate prose. A recommendation record includes:

- a deterministic recommendation ID and its report issue ID;
- the evidence-derived target agent/action;
- catalog version/digest and recommendation kind;
- `new_gap`, `review_existing`, or `unavailable` mapping status;
- applicable current-control identities without claiming semantic equivalence;
- the inert intended constraint in the catalog's closed vocabulary;
- expected protected behavior; and
- a non-executable future verification recipe expressed as expected behavior,
  authoritative evidence roles, and pass/refusal criteria—never commands.

If evidence cannot resolve an action, a target seam is absent/opaque, or a
current control cannot be compared safely, retain the issue and say exactly
what is unavailable. Do not infer that an existing control addresses the issue,
that OpenBox blocked prior behavior, or that a suggested control will enforce
the expected result.

## Self-contained report pack

Seal `ai.openbox.project-security-report/v1` with this frozen inventory:

```text
observation/run.json
observation/backend.json
observation/openshell.jsonl
observation/effects.json
observation/behavior.json
observation/coverage.json
observation/manifest.json
analysis.json
standards.json
recommendation-catalog.json
target-posture.json
report.json
report.md
report.sarif
manifest.json
```

The observation directory is an exact embedded copy of the verified Phase 2
pack. `analysis.json` is the exact accepted Phase 3 input. The catalog and
projection identities are content-addressed by the top-level manifest, which
is written last. No links or extra files are allowed. The pack is owner-only
and remains sensitive because candidate prose and embedded observation content
may contain retained prompts or outputs.

All three report projections derive from the same normalized objects. They use
stable lexical ordering, stable content-addressed issue/rule/result IDs, and
one newline convention. SARIF includes artifact locations only when evidence
supplies a real safe location; otherwise it omits the location. A copied input,
catalog, posture, projection, manifest, permission, or file-set mutation fails
verification.

Given a sealed report pack, repeated verification and rendering are byte-stable
and make no network or model call. Separate live finalizations may truthfully
differ when current target posture or its capture window changes.

The human report makes the authority chain explicit:

```text
observed behavior -> validated issue -> standard
  -> evidence-derived OpenBox target/action -> observed read seam/current posture
  -> inert recommendation or honest unavailable mapping
  -> expected protected behavior -> future verification recipe
```

## Stop conditions

Do not publish a report if observation or candidate integrity fails; a cited
claim cannot be grounded; the target identity, permission, safe read seam, or
posture snapshot cannot be reconciled; control state drifts during capture;
unsafe or executable control content would be retained; projections disagree;
historical bytes drift; cleanup is incomplete; or any Phase 4 path can apply a
recommendation, decide an approval, or call an OpenBox write route.

Do not turn an unavailable recommendation into a report-wide false negative.
Retain the validated issue, mark the mapping unavailable, and disclose the
missing authority.
