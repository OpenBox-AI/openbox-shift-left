1 Verdict
Sound — proceed, with three corrections before phase 01 closes

The plan's structure is right and its central judgement is right: phase 02 is the precondition, not cleanup. Rebuilding the guards while the module boundary still exists — with both forms green in one commit as the equivalence evidence — is the correct ordering, and the stop condition ("if a phase-02 drill comes back green, phase 03 does not start") is the correct gate.

Every structural claim I could check against the tree holds. What does not hold is a set of counted quantities the plan turns into acceptance gates, and two places where the plan's own reasoning is right but its enumeration is short. Those are findings G1 G2 G3 G4 below.

15 modules, 45 replace directives, 19 distinct direct external deps, 5 go.mod-reading guards, 3 suspect cmd/ trees, 61 shell testbed refs, both committed probe binaries, dir: cli + GOWORK=off, the two vacuous CI steps. All present exactly as described.

Gaps

The one argument ADR-0011 did not have available

The plan's strongest claim is empirical rather than aesthetic, and it checks out: cli imported transport with a require and no replace; all 14 modules reported green in the workspace while GOWORK=off — the only path .goreleaser.yaml takes — could not resolve the import at all. Deleting go.work deletes that entire divergence class, not one instance of it. That belongs in the commit message exactly as the plan says.

And the honest counterweight is stated, not averaged. ADR-0011 reason 2 — "adapters must not import each other" — was mechanical because they were separate modules. Under internal/adapters/ both are siblings and the compiler permits the import. It becomes a test in layering_test.go or it becomes nothing. The plan records this as a real downgrade rather than a wash, which is the standard this repo holds itself to.

6 Gaps found
G1 high phase 05, phase 06 silent failure
Three source-relative path constants break on the move. The plan names one, and the unnamed pair includes a test that fails by skipping.

Phase 05's key insight is exactly right — "this is the one place in the plan where a wrong path compiles fine and fails only when the conformance suite runs" — but the enumeration is short. There are three, and the two the plan misses are worse than the one it names, because neither is reached by the conformance suite it proposes to count.

grep -rn '"\.\./' --include='*.go'
contracts/dev-event/conformance/schema.go:21
  const schemaRelPath = "../schema/dev-event.schema.json"        ← plan names this

cli/internal/gatewayemit/contract_test.go:23
  const schemaRelPath = "../../../contracts/dev-event/schema/…"  ← NOT named

adapters/common/devconfig/managed_test.go:204
  const template = "../../../deploy/managed/openbox/dev.json"    ← NOT named

The devconfig one is the dangerous member. Its depth changes under phase 03 (adapters/common/devconfig → internal/adapters/common/devconfig, three segments to four, so ../../../ stops resolving at the repo root) and its target directory is renamed by phase 05 (deploy/ → deployments/). Two independent breakages on one line. And its failure mode is:

adapters/common/devconfig/managed_test.go:205
if _, err := os.Stat(template); err != nil {
    t.Skipf("template not present: %v", err)     ← SKIPS. Does not fail.
}

This is the repo's own documented failure mode, in a new place: a capability guard that makes a test honest also blinds its author. TestManaged_ShippedTemplateLoadsAndLocks exists to prove the shipped managed template loads and asserts enforce — its own comment says the failure it prevents is "silently unmanaged". After the move it would stop proving that, report SKIP, and the suite would stay green. Phase 01's baseline records skips separately, so a skip-count delta would surface it — but only if someone reads the skip column, and phase 03's success criterion 4 is written against declared and verdict counts, where a skip still counts as a verdict.

The gatewayemit one survives by luck. cli/internal/gatewayemit → internal/cli/gatewayemit keeps the same depth, so ../../../ still lands at the repo root — but its target moves to api/ in phase 05, so the constant still needs editing. It resolves through runtime.Caller, so it fails loudly rather than silently. Note its comment explains it reads the schema with stdlib precisely because the conformance package "is not a dependency of this module" — an argument the collapse dissolves, which is worth a line in ADR-0024.

Why the plan's own sweep does not catch these

Phase 05 criterion 1 ("no path reference anywhere names testbed/, deploy/, or the old schema location") would catch both — but the sweep that implements it, in phase 06 step 6, is scoped to *.md, *.sh, *.yaml, *.json. *.go is not in the list.

Recommended correction. (a) Add all three constants to phase 05's Related code files and its todo list. (b) Add *.go to the phase 06 sweep file-type list. (c) Add a phase-05 criterion that TestManaged_ShippedTemplateLoadsAndLocks runs — not that the suite is green. (d) Cheapest structural fix, if you want one: resolve both test paths through runtime.Caller like conformance/schema.go already does, so a wrong path is a hard failure rather than a skip.

G2 high phase 02 control weakened silently
One of the six guards is not equivalent under the replacement — and both of phase 02's equivalence criteria would report green while it is narrowed.

Phase 02 replaces five go.mod allowlists with "the non-stdlib, non-repo import paths appearing in the files of a subtree". For four of the five that is a fair analogue. For contracts/dev-event/conformance/deps_test.go it is not, and the guard's own comment says why.

contracts/dev-event/conformance/deps_test.go:34
var allowedDependencies = map[string]bool{
    "github.com/santhosh-tekuri/jsonschema/v6": true,
    "golang.org/x/text":                        true,   ← // indirect in go.mod
}

// go.mod is the whole gate: a Go module cannot import what it does not require.

golang.org/x/text appears nowhere in the subtree's Go source. It is an // indirect require, and the guard reads every require line — that is the point of it. A direct-import AST scan cannot see an indirect dependency at all, so:

  • the x/text entry becomes vestigial — present in the allowlist, unreachable by the check;
  • the guard's stated purpose — "a convenience import here spreads to three other modules, so adding to it is a decision" — stops covering the case where the new arrival is transitive, which is the case that spreads furthest;
  • its replace prohibition ("a replace would make this contract module resolve differently per checkout") becomes inexpressible. Moot after phase 03 deletes every replace, but it should be recorded as retired rather than lost.

The reason this matters more than the individual entry: phase 02's equivalence evidence is (1) both forms green in the same commit and (2) allowlist contents byte-identical. Both hold here. The old guard passes because x/text is on the list; the new one passes because it never looks. Byte-identical contents, green co-residency, and a control that got quieter — the exact shape phase 02's own risk table calls "replacement passes for a reason other than the one it names", which the plan otherwise handles well.

The three prescribed drills do not separate the two either: delete-the-guard → red, add an unreviewed direct import → red, add a repo-local import → green. None adds an unreviewed indirect dependency.

Recommended correction. Add a fourth drill case for this guard only: pull in a package whose dependency arrives transitively, and confirm the replacement fires. If it does not — the likely outcome — then either keep a root-go.mod allowlist alongside the subtree scan for the conformance dependency floor, or record in the ADR-0023 amendment that the indirect half of that floor was retired with the module boundary. Both are defensible; silently narrowing it is not, and this repo's rule is that an added or removed allowlist entry needs the ADR amendment first.

G3 medium phase 01, 05, 07 gate cannot close
Counted quantities are carried into acceptance gates without being re-derived. The largest is off by 26 lines.

Phase 01 step 6 reads: "confirm the changed-line count reconciles with the measured 444 import lines + 45 replace lines." Measured at review time: 418 import lines across 200 files. The replace count is exact at 45. So the reconciliation gate, run literally, fails on a correct rewrite — and the natural response is to widen the tolerance, at which point the gate stops distinguishing "the map is complete" from "the map is nearly complete", which is the only thing it exists to do.

The same class appears three more times, each smaller: phase 05's 34 markdown lines (measured 59, or 39 excluding CLAUDE.md's dated status records — which phase 06 correctly puts on the do-not-touch list, so the live figure needs stating separately); 6 deploy/ markdown lines (measured 7); 21 testbed scripts (measured 17 at the top level).

And one small self-conflict worth resolving before phase 07 runs: it commits to fixing "the three pre-existing filename deviations", but only two live in tracked Go source (consts_paths.go, enforce_evaluate.go). The third match in the tree is plans/260825-0027-…/probes/probe-server.go — inside plans/, which phase 06 explicitly protects as a stateful record.

Recommended correction. These numbers are cheap to re-derive and phase 01 is already the phase that derives them. Change step 6 from "reconciles with 444 + 45" to "reconciles with the count captured in step 4", and let the baseline own every figure the later phases gate on. That also makes the plan immune to the tree moving between writing and execution — which it already has.

G4 medium all seven phases guard cannot fire correctly
The corruption check every phase depends on returns 25 hits on an already-clean tree.

Every phase carries the same security step, and it is the right instinct — this repo has four demonstrated victims of the enforce-path redactor rewriting a file on write, including a Go source file whose Ed25519 test vector was silently replaced. A bulk rewrite of 200 files inside a governed session is exactly when to check. But the check as written cannot pass:

the plan's control, run verbatim on the current clean tree
$ grep -rn '\${OPENBOX_REDACTED_' . --exclude-dir=.git --exclude-dir=plans --exclude-dir=docs | wc -l
25

Those 25 are legitimate: the redactor's own replacement template and documentation in decision/secrets.go, its test fixtures, and the adapter and gateway tests that assert the marker appears. The marker is a normal string in the source of the thing that emits it.

So the phrasing — "grep must return nothing outside plans/ and docs/; treat a hit as corruption, not as a finding" — leaves an operator two options, and both are bad. Chase 25 non-findings after every bulk operation across seven phases, or learn to ignore the output, at which point a real 26th hit lands in noise. An unfireable guard reads as coverage — which is the failure phase 07's own risk table names for the CI documentation check, applied here to a security control.

Recommended correction. Make it a differential rather than an absolute: capture the hit set during phase 01's baseline and assert equality afterwards, so a new occurrence is the signal. git diff --name-only piped through the grep is the cheaper form and is strictly better for this purpose — corruption arrives on a written file, so scanning the whole tree was never the right scope.

7 What the plan gets right
Ordering

Guards rebuilt before the boundary is removed, both forms co-resident in one commit as the equivalence evidence, with an explicit stop condition. Doing this after the collapse would leave no green state to compare against — the allowlists would already be failing, and "fixing" them by widening to the union is precisely the silent-destruction path the plan names.

Nested internal/ preserved

gateway/internal/dialhook → internal/gateway/internal/dialhook. Flattening it would silently widen a seam that exists to be narrow. The plan spots that the nested form still restricts importers to the internal/gateway/… subtree — the exact property dialhook was built to have.

Verdicts, not pass counts

The baseline counts declared tests against verdicts, per package. This repo has been bitten twice by tests that produced no verdict at all and were invisible rather than failing; reusing the established local method rather than inventing one is right.

Criterion 3's subtraction

"Baseline minus the tests belonging to the trees D5 deletes, enumerated by name." Without that clause the acceptance criterion would contradict D5, since the deleted trees carry main_test.go files. Catching a self-contradiction between a decision and a criterion, in the same document, is the part most plans miss.

"Grep is not the check"

The reachability gate demands an install-or-invocation path per tree, not an absence of identifier hits — because a binary name held in a settings JSON string or assembled by concatenation never appears as a Go identifier. Deletion on a proved negative only.

Phase 04 discharges R1 honestly

Executing the snapshot binary, not merely building it, is the coverage ADR-0011 said did not exist. And phase 06 requires ADR-0024 to say the revisit condition was met concurrently rather than as a precondition — an owner decision, not a technical discharge. That distinction is what keeps the ADR from reading as a pure win.

D4's three independent arguments

Keeping install.sh at the root is argued from the source's own /build text, from curl | bash making $0 not-a-path so no dirname shim can work, and from scripts/ otherwise holding one file. Three arguments, one conclusion — and a recorded reason so the next reader does not "finish the job" and break the documented install URL.

init/ stays documentation-only

Rejecting go:embed for the unit bodies on the phase-12 election precedent — a second store of derivable state whose drift is silent — rather than on the source README's literal wording. Two live silent failure modes are named (a plist missing StandardErrorPath; an ExitTimeOut that stops matching --shutdown-grace), which is what makes it a decision instead of a preference.

9 Questions and recommendation

Carried from the plan, still open

  1. ext-core/ disposition. Plan assumes delete, ADR-0004 being the surviving record. Verified: it is a single README.md tombstone. Delete is the right call — a duplicated retirement note in a disappearing directory is a drift surface. No objection.
  2. If the phase-03 gate finds a suspect binary reachable, does it stay in cmd/ or move to tools/? The plan's rule ("a product path keeps it in cmd/, a test or dev path moves it to tools/") is sound and needs no further decision now.

Raised by this review

  1. Does the conformance dependency floor keep its indirect half? (G2) Keeping it means one root-go.mod allowlist survives the collapse alongside the six subtree scans. Retiring it means the ADR-0023 amendment says so explicitly. This is a security-control scope question, so it is an owner call, not an implementation detail.
  2. Should the two unnamed relative paths be made loud rather than merely corrected? (G1) Switching managed_test.go from os.Stat+Skipf to a runtime.Caller resolution and a hard failure is a behaviour change to a surviving test — technically outside "this is a move-and-rename refactor". It is the difference between fixing this instance and closing the failure mode.
  3. Phase 07's third filename deviation resolves to a file inside plans/, which phase 06 protects. Drop the count to two, or state the exception.
  4. Should the corruption check become a differential? (G4) It is repeated as a security step in all seven phases, so the form it takes is worth settling once, in phase 01, rather than being re-copied six more times.
Recommendation

Proceed. Fold G1, G3 and G4 into phase 01 — all three correct artefacts phase 01 produces anyway: the path map, the baseline, and the corruption check it establishes for every later phase. Phase 01 mutates no Go code, so the cost is an hour of editing rather than a re-plan.

Resolve G2 before phase 02 is written, not after its drills run. It changes what one of the six replacements has to do, and phase 02's whole value is that it is the phase where a weakened control is still visible. After phase 03 the evidence that would reveal it — a green original standing beside a green replacement — no longer exists.
