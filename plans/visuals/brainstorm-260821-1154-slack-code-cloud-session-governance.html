Brainstorm contract · 2026-08-21 · openbox-shift-left

Slack Code doesn't move the code.
It moves the machine.

Slack Code lets a team tag a coding agent in a channel and watch it work in the open. For Claude Code that tag routes to a cloud session — a fresh Ubuntu VM on Anthropic infrastructure, not the developer's laptop. Every governance mechanism this repo ships is provider-agnostic Go that would run there fine. Exactly one thing stops it, and it is four lines of install path.

00 · The contract

Outcome

A Claude Code session initiated from Slack is governed by the same pipeline a local session is: events in governance_events, gated calls decided by /evaluate, and the product tells the truth when it is not governed instead of reporting success.

Constraints
  • Reuse, don't rebuild — new table/endpoint/service needs an ADR.
  • Cloud VM sees committed files only; Ubuntu 24.04 x86_64.
  • Org-shared environments have no secrets store (documented).
  • --yagni: cut anything the outcome doesn't need.
Non-goals
  • Any Slack app, bot, or Code Channel API surface.
  • Governing the other Slack Code agents (Devin, v0, Copilot, ChatGPT).
  • An approval UI inside Slack.
  • Changing activity_id / event identity.
Acceptance
  • A1 A channel-initiated session produces events in core.
  • A2 A gated call in that session gets a real verdict.
  • A3 An unreachable core is reported, never silently failed open.
  • A4 No duplicate engine when a repo-scope and a local-scope install coexist.

01 · What actually happens when someone tags @Claude

Slack Code (GA 2026-08-20, any Slack plan) opens a Code Channel, spins up an agent space, and renders diffs and a live preview on a canvas for the team to sign off. That is Slack's half. Anthropic's half is the part that matters to us: a coding mention routes to Claude Code on the web, and on Team and Enterprise plans that is being consolidated under Claude Tag, where @Claude acts as the organization's shared identity. Claude Tag channel sessions run in organization-shared cloud environments only.

The good news is most of it. Anthropic documents that a cloud session carries the repo's CLAUDE.md, its .claude/settings.json hooks, its .mcp.json, and its .claude/skills|agents|commands — all "part of the clone" — and that org policy arrives separately through server-managed settings, which also apply inside cloud sessions. A setup script runs as root before Claude launches and is filesystem-snapshot cached. install.sh already detects linux/amd64; CI already builds it on ubuntu-latest. Nothing in hookflow needs to change.

02 · Three mechanical reasons we govern nothing today

openbox init at project scope writes <dir>/.claude/settings.local.json (adapters/claude-code/localhooks.go:90). That file is by design the per-developer, git-ignored one — correct for a laptop, and invisible to a fresh clone. A Slack-initiated session therefore starts with no OpenBox hooks registered at all.

The supervision pass corrected an earlier draft that called this "the single blocker." It is three, and the other two are the kind that fail silently:

  • The file layer. No committed file names our engine.
  • The binary must be on the VM's PATH. A portable hook entry pointing at a binary the setup script never installed reproduces the unquoted-path failure exactly: hooks never start, and the install still reports success.
  • HOME mismatch. The setup script runs as root; Claude Code runs as another uid, so ~/.openbox/ and the spool fallback resolve elsewhere. This one already has a first-class mitigation: OPENBOX_HOME, whose own doc comment names "containers with an unusual HOME" (devconfig/paths.go:27-30).

So this is not a missing scope so much as a missing target. And the correction that shrinks the whole plan comes next.

The discovery that shrinks the plan: credentials and posture already work entirely from environment variables. devconfig defines env constants for every credential (OPENBOX_API_KEY, OPENBOX_AGENT_PRIVATE_KEY, OPENBOX_AGENT_DID, OPENBOX_AGENT_ID, OPENBOX_BASE_URL, OPENBOX_BACKEND_URL) and for every posture key: EnvEnforce, EnvFailClosed, EnvContentCapture, EnvRealtime, EnvEnforceTimeout, EnvFindings, EnvSecretDetection, plus EnvSpoolDir and EnvHaltDir (devconfig/devconfig.go:45-82).

So the cloud recipe is: org environment variables + a setup script that only drops the binary + committed hooks. No openbox auth, no dev.json, and no committed posture, which means posture stays org-controlled without anyone committing it to a repo. That deletes most of the fragility above and most of the recipe.

The network gate is still the one that should worry us most. The default Trusted network level allowlists package registries, GitHub and cloud SDKs. The OpenBox core hostname is not among them, and there is no organization-level allowlist an admin can push to every environment — each environment carries its own list.

So a naive install yields: observe events spooled and never delivered; gated calls reaching ApplyFailurePolicy with no verdict; and under the default fail_closed:false, every gated call fails open. A cloud session that reports a successful install and governs nothing. That is precisely the ADR-0016 pattern — "the old default reported success while governing nothing" — and this repo has been bitten by that shape before.

03 · Which vehicle carries the hooks

Three committed-or-managed paths can register our engine in a cloud session. They are not equivalent.

RankVehicleStrengthFails first when
1 Server-managed settings Org-wide, applies inside cloud sessions, survives a developer editing the repo. The org-scope activation this repo currently says it cannot perform. We cannot write it — it is an Anthropic admin surface. So it is a documented deployment step, not code. Same gap as today's managed-settings note.
2 Committed .claude/settings.json The one thing init can actually produce end-to-end. Travels with the clone into any VM, local or cloud. Per-repo, and a developer can edit or delete it. Needs a path-independent engine invocation — an absolute /Users/… path is meaningless in the VM.
3 The existing plugin plugin/hooks/hooks.json Already declares all 11 events plus asyncRewake. Zero new authoring. Plugins install at session start from a marketplace over the network — and constrained network is exactly the problem. Under Trusted the marketplace may be unreachable, yielding no hooks and no error we own.

04 · Three approaches

Option A · docs only

Ship a reference environment recipe

A docs/ page: the setup script, the Custom allowlist entries, the settings snippet to commit. Zero repo code.

Depends on — users hand-editing a settings file correctly.
Fails first — someone follows the recipe, leaves network on Trusted, and governs nothing without knowing. No doctor to catch it.

Option B · recommended

A committed target on project scope, plus a doctor probe

Not a third scope: a target flag (--shared) on the existing project scope. Global's defining property is that it writes no project file, and a committed settings file is still a project-directory write. One install path, one filename decision, one ownership rule.

Depends on: the file set becoming the unit of ownership, not one hardcoded filename.
Fails first: not where the earlier draft said. See the correction below.

Option C · rejected

A Slack-side integration

A Slack app that posts verdicts into the Code Channel and offers approval buttons.

Depends on — a third-party Code Channel surface. Launch coverage mentions only "APIs to third-party agents and harnesses"; no public SDK was found.
Fails first — the surface turns out to be partner-gated and the work is unbuildable. And it buys no governance coverage beyond B — only approval UX. New service ⇒ ADR ⇒ against reuse-don't-rebuild.

Recommendation: B, gated behind a probe. The whole architectural read is that we govern the cloud environment, not Slack. Slack Code is a front door; the thing that executes tools is a Claude Code session, and this repo already governs Claude Code sessions. Coverage of Slack-initiated work falls out for free the moment the hooks are in a committed file and the host is allowlisted — with no Slack API surface at all. That is the --yagni answer, and it is also the correct one.

04b · The correction that matters most

An earlier draft named the duplicate-engine risk as "a portable entry coexisting with an absolute-path entry reads as two engines." That is wrong, and checking it is what found the real hole.

Not a risk — verified

Within one file the classifier is already correct. sweepStale compares each owned handler's engine token against want and drops the mismatches (localhooks.go:374-381) rather than preserving them. And splitEngineToken explicitly handles a bare unquoted word, its own comment naming "the openbox-on-PATH fallback" (localhooks.go:437-457). Portable-vs-absolute in one file is replaced, with a printed notice.

The real hole — cross-file

Both the write path and the audit path hardcode one filename (localhooks.go:90 and :276). Searching adapters/ and cli/ for the committed filename returns nothing: no code names it at all.

Claude Code merges hook layers additively. A committed file plus a pre-existing local file from any earlier init means both engines fire, every governed call stores twice, and openbox doctor is blind because AuditLocalHooks never opens the other file. That is the 2026-08-14 double-count defect restored in the one shape its fix cannot see.

Fix shape, in this repo's own precedent. The 2026-08-14 lesson was that a check and its remedy must be built on one classifier. Extend that: make the file set the unit. writeLocalHooks and AuditLocalHooks both take an ordered set of candidate settings files, classify across it with the same ownedLocalHook, and enforce one owner file — writing the committed target removes our entries from the local one, and reports what moved. Do not let both hold ours on the theory that it is harmless. It is not: it double-stores.

07 · The decision only a human can make

One item here is a genuine OD*: it is a privacy and attribution choice, not something to infer.

OD · identity in a shared environment

This repo's agent is machine-scoped (kind=developer, one per machine, ADR-0015 / ADR-0016). A cloud session has no durable machine, and under Claude Tag it does not run as any member — it runs as the organization. So:

  • One agent per shared environment. Every member's Slack-initiated session signs as the same agent. Attribution degrades from which developer to which channel or environment.
  • One agent per developer. Needs a per-user secret in a shared environment that Anthropic documents as having no secrets store. Not achievable with the documented mechanism.

The workable answer is the first, stated honestly. And a runtime key placed in a shared environment's variables is a fleet-wide plaintext key readable by every session in that environment and by the agent itself. ADR-0015 accepts plaintext for one machine; this is the larger blast radius CLAUDE.md already names for approver installs. If we go here, it should be a dedicated low-privilege cloud agent key — never the org or approver key.

08 · Risks, and what is already true

Already true — no work needed
  • linux/amd64 is built (CI on ubuntu-latest) and install.sh detects it.
  • hookflow, the mapper, AIP signing and activity_id are untouched.
  • A HALT already surfaces in the channel via continue:false.
  • The plugin already declares all 11 events.
Open risks
  • Spool loss, not spool delay. If core is unreachable and the VM is destroyed at session end, events are lost, not queued. OPENBOX_REALTIME is therefore mandatory in the cloud, not an optimization, and a hard teardown still loses the SessionEnd tail.
  • A REQUIRE_APPROVAL policy without the autonomous approver is effectively bricked: it taxes every prompt for the hold timeout, then denies. ADR-0012's approver is headless by design, so the recommendation is approver-or-no-approval-policy, not "approval is unfixable in cloud."
  • HALT latch lost on resume: halted-sessions/ holds within one VM, but a resumed session gets a fresh VM. Narrow, real, needs naming.
  • Anthropic's DNS audit trail sees our egress hostnames — worth stating in data-and-privacy.md for a governance product.
  • Claude Tag cannot use self-hosted environments yet, so the strongest isolation option is unavailable to exactly the surface Slack uses.

The load-bearing assumption is that a committed .claude/settings.json hook actually fires in a Claude-Tag-initiated channel session, and that the engine can reach OpenBox core from that environment. Both are documented; neither is verified here. The probe in Phase 0 tests both at once for about thirty minutes of config and no repo code — which is this repo's own standard: reading the docs is not evidence that a hook fires.

Unresolved questions

  1. Does a Claude-Tag channel session execute a repo-committed .claude/settings.json hook, and is there any interactive trust prompt for committed hooks that a headless session cannot answer? Documented yes and no respectively; both unverified. Phase 0 answers them with a marker file and no credentials.
  2. Does Claude Code merge hook layers additively across a committed and a local settings file? The cross-file double-store risk depends entirely on this. Verify it in Phase 0 alongside the trust question.
  3. Do we accept environment-scoped agent identity, losing per-developer attribution for Slack-initiated work? This needs an ADR-0015 amendment, not a footnote: one org-shared key means one agent id and one signing key for every cloud session, readable by every member and by every governed agent. (OD.)
  4. Should the cloud posture default to fail_closed:true, accepting that an unreachable core denies every gated call? And should a cloud environment be required to run the ADR-0012 approver before any REQUIRE_APPROVAL policy is allowed to apply to it?
  5. Who owns the org-shared environment config in a customer org, and can OpenBox verify the allowlist step remotely or only advise?
