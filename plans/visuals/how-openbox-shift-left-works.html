How OpenBox Shift-Left works

You code with Claude Code or Codex the way you always do. One static Go binary watches, evaluates, and records everything the session does — through the same OpenBox pipeline your org's production agents already report to.

01The mental model
Your coding agent is treated like any other agent in the org: registered, observed, subject to policy, and able to prove what it did.

Shift-left is the developer-runtime half of OpenBox governance. Your machine is registered as an OpenBox agent (kind=developer), every coding session becomes a child record, and everything the session does — prompts, tool calls, model calls, token spend, outcomes — flows to the same control plane, the same /api/v1/governance/evaluate endpoint, and the same storage the production agent runtime uses. There is no parallel pipeline; that is the core design rule (reuse, don't rebuild).

It does three jobs. Observe: a normalized event stream of everything the session produced. Enforce: the control plane can allow, deny, require approval for, or halt what the agent is about to do — before it does it. Prove: commits carry signed attestations that link code back to the governed session that wrote it, through CI, to the deploy.

Two components run on your machine: a hook engine that Claude Code/Codex invoke around every event of a session, and full-capture plan an OpenBox gateway that sits in the model-call path itself (Claude Code → gateway → api.anthropic.com) — the only vantage point that sees raw HTTP headers and bodies, and the only one that can refuse a model call before it leaves the machine.

02Setup — two commands, then forget it

Setup deliberately splits machine identity from project wiring (that decision/0016). You authenticate a machine once; you initialize each project you want governed.

once per machine
$ openbox auth
Registers (or reuses) this machine as an OpenBox agent. Writes two files with one job each: ~/.openbox/.env holds secrets — the runtime key and signing key, plaintext, 0600 on macOS/Linux, deliberately — and ~/.openbox/dev.json holds coordinates: your DID, agent id, backend URL. A DID in .env is ignored by design.
once per project
$ openbox init --provider claude-code
Installs the 11 hook registrations into the project's .claude/settings.json (project scope, enforce ON — both defaults) and writes posture. It only ever touches entries it owns — ownership is decided by argv shape, and stale registrations from old installs are replaced, never duplicated. full-capture plan Also writes the gateway routing (ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN) at user scope, because project files can't carry it; fleets distribute the same block via managed settings.
when something looks off
$ openbox doctor
Read-only diagnosis: are credentials present, is the control plane reachable, which scope is active, is a duplicate hook engine registered (it warns and init repairs), and full-capture plan is the gateway reachable and would a bypass currently succeed.
What "governed" means for you day to day: nothing changes in how you drive the agent. Hooks fire around what the session already does; the gateway is byte-transparent to the model conversation. You notice governance only when a policy decision says no — and the refusal tells you why.

what the events become
  • Tool call/result → ActivityStarted/ActivityCompleted, span-less, with status: completed|failed
  • Model turn → an llm_completion activity pair with token usage + model id, the assistant text on one span
  • Denials, subagent starts, API errors → metadata-only signals — never signal_args, which core would read as a new user goal
  • full-capture plan Model request/response → SpanData with request_headers, response_headers, bodies, http_*
ordering that matters
  • Spool first, deliver second: a crash over-reports into core's dedupe rather than losing an event
  • Near-real-time delivery via a debounced background flusher (OPENBOX_REALTIME=0 to disable)
  • Redaction runs before content is attached — conformance asserts it on the outbound bytes, not in unit logic
  • Subagent turns are partitioned by isSidechain; a turn is never counted twice
05What gets captured

Full capture is the org's default posture — an owner decision. One gate governs all content classes: content_capture, ON by default. Everything content-bearing is secret-scanned and redacted locally before it leaves your machine, then capped at 64KB.

Be aware of what "on by default" means: with capture on, the control plane sees your prompts, your code as the agent reads and writes it, the model's reasoning, and every tool result — redacted of detected secrets, capped at 64KB per item. That is the point of the product, and it is an org-level decision, not something the tool sneaks in. docs/data-and-privacy.md is the authoritative statement of what egresses when.
06What can stop you — enforcement

Every verdict comes from the control plane (/evaluate is the only decider — that decision deleted the local policy engine on purpose). Your machine renders verdicts; it never makes them. Four levers, in the order you'd meet them:

1 · prompt gate
Your prompt is evaluated before the agent sees it
UserPromptSubmit runs the same gate as tool calls. BLOCK erases the prompt with a reason; HALT ends the session on the spot.
2 · tool gate
Gated tool calls wait for a verdict
PreToolUse sends every policy-gated class to the server — shell, file writes, MCP, all of them; the client does no local narrowing. DENY blocks the call and the agent is told why. If the control plane is unreachable, the default posture (fail_closed:false) lets calls proceed ungoverned; a fail-closed org denies instead.
3 · approvals
REQUIRE_APPROVAL holds, then resumes
The call parks while a human — or the autonomous approver — decides; the rewake watcher resumes the session on a decision. Approval identity is deliberately conservative: shell and MCP approvals survive a retry, every other class re-asks. Over-ask, never over-grant.
4 · halt
HALT ends the session — and keeps it ended
A server HALT stops the turn and writes a local latch: every later gated hook in that session is refused with no re-evaluation, resume included. On Codex, HALT renders as a deny (session kill is a follow-up).
5 · model-call gate full-capture plan
A model call can be refused before it leaves the machine
The gateway asks /evaluate for policy-marked calls and refuses on verdict — with a response shape chosen so the tool surfaces the reason instead of retrying. The gateway can forward or refuse, nothing in between: it never rewrites or sanitizes a request (inspect-without-modifying).
the trade you accepted
Availability inversion
With the gateway holding the org's provider credential, bypass fails — no gateway, no key, no model access. The flip side is deliberate: a gateway outage stops development. Tamper-resistance and fail-open are mutually exclusive; the org signed this trade in.

What the signature proves — and doesn't: the signing key lives in a file readable by anything running as you, including the governed agent itself. 08What it can't do

This product's own rule: an overstated governance claim is the failure it exists to prevent. These limits are documented, deliberate, and worth knowing before you rely on the system (docs/architecture.md#assurance).

  • A default install governs one directory. Absence of events is not evidence of absence of work — a session in an uninitialized directory produces nothing.
  • Hook-path enforcement needs the control plane. Under the default fail_closed:false, blocking one hostname disables it. Model-call governance doesn't share this weakness once the gateway holds the credential — but hooks still ride config.
  • Content policy sees at most the first 64KB of any single item.
  • Redaction is local pattern + entropy detection — the only in-transit control. Guardrail redaction at source is not wired; secret_detection:false means unredacted egress.
  • The gateway inspects or refuses; it never sanitizes. Rewriting a request would break the tool's header/body pairing — so redaction-at-source is structurally unreachable at that layer too.
  • A few calls never traverse the gateway: the tool's availability probe and its URL-safety check go to api.anthropic.com directly, regardless of base URL.
  • Codex is thinner: usage per session rather than per turn, no tool success signal, HALT renders as deny, and no gateway equivalent in v1.
  • CI sessions are not gateway-governed — there's no service-token sign-in flow; CI is covered by the lineage action instead.
  • Thinking capture rides an undocumented transcript format. If a tool release changes it, capture degrades silently to none (alarmed in the testbed, never an error in your session).
  • Goal-alignment widgets need extras: finops ∧ content_capture (both default-on) plus a reachable LlamaFirewall and Redis on the control plane — without those they stay empty with a perfect client.

10Where things live

Eleven Go modules under one workspace (twelve with the gateway), tied together by go.work. The history lives in git and — read decision records for why, code for what is true now.

│   ├── common/hookflow/         — the engine every adapter runs on: spool, gates,

│   ├── common/devconfig/          — posture resolution (config + env), shared

├── contracts/dev-event/           — event schema v1.x, wire mapping, conformance
├── actions/openbox-git-action/    — commit → deploy lineage for CI
├── testbed/                       — mock-free e2e against a real local stack
└── docs/ — architecture, data-and-privacy, decision records 0001–0021
The repo's evidence culture, in one sentence: unit tests are not evidence that a hook works — testbed/run-all.sh drives real headless sessions against a real local stack and asserts what actually arrived, and every feature's docs say plainly which claims that run has and hasn't yet proven.
