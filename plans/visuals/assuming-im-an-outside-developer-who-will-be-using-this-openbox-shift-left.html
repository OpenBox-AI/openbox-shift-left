OpenBox Shift-Left

an outside developer's guide — what it does · how it works · how to set it up and run it

01 What it is

Governance for the coding agents you already use. OpenBox governs AI agents at runtime; Shift-Left extends that same pipeline one step earlier — to Claude Code, OpenAI Codex and other agentic tools that write the code. For any commit or deploy, your org can answer: who produced this, with which tools and prompts, at what cost — and was it allowed?

It is one static Go binary that installs itself as native hooks inside your coding tool. By default there is no daemon, no proxy, no second dashboard, and nothing you have to keep running. Sessions emit normalized telemetry to your org's OpenBox; risky tool calls and prompts are decided by your org's policy before they run; commits get a lineage trailer and a signed attestation. Opt-in, a local gateway relays the model calls themselves — the one surface hooks cannot see (section 04).

Two paths, deliberately separate
Gated calls block on a verdict
Every gated PreToolUse call and every submitted prompt is evaluated by /evaluate before the tool runs. One policy implementation, on the server — nothing evaluates policy on your machine (ADR-0017). If OpenBox is unreachable, fail_closed decides: the default is fail-open, so an outage never blocks work.
Telemetry never blocks anything
Events are spooled locally and drained by a detached, debounced flusher within ~2s of each tool call. A slow or absent OpenBox cannot slow a tool call; undelivered events are retried, not dropped. SessionEnd flush is the completeness safety net.
One engine, thin adapters
Everything provider-agnostic lives in one engine (hookflow); each tool adds a thin adapter behind one SPI — its native hook shape, a mapper, an output contract, an installer. Adding a tool is an adapter, never a fork.
Same pipeline as the agent runtime
Dev sessions register as OpenBox agents (kind=developer), sign with the same AIP scheme, hit the same endpoint, and land in the same tables as production agent-runtime sessions — one dashboard, not two.

04 Governing the model call itself — the opt-in gateway
Why hooks are not enough

Hooks see what the agent does. They cannot see the model call itself — no hook carries the request headers, the request body, or the response — so system prompts, raw request/response bodies, and which account paid for a call are all structurally unreachable from the hook path. The gateway (ADR-0021) is the surface where those exist: a per-developer loopback daemon that Claude Code is pointed at via ANTHROPIC_BASE_URL. Every model call relays through it to Anthropic; the gateway reports to the same /evaluate as everything else. It is off by default — it redirects live model traffic, so turning it on is your call:

openbox init --provider claude-code --gateway # install + start it, and point this machine at it openbox init --provider claude-code --remove-gateway # undo — restores direct provider traffic openbox gateway # the daemon itself: foreground, supervised by launchd/systemd
Model-call capture
Request and response evidence for the call itself — the last large capture gap hooks cannot reach. Credential headers (Authorization, x-api-key, Cookie…) are replaced with [redacted] by name before anything is attached; the key is kept so a reviewer can see one was sent. Gated by content_capture.
Refusing the inference itself
The hook path can refuse a tool call; only the gateway can refuse the model call, synchronously, before it leaves the machine — on a verdict from /evaluate, never on local rules.
Account binding
A truncated SHA-256 fingerprint of the credential that actually paid — deliberately not gated by content_capture, because a privacy switch that removed it would let an org opt out of being identified. Core policy (not gateway logic) can HALT a call from a non-org account.
Four guarantees, by construction
Pass-through auth: OpenBox holds zero provider secrets — your credential relays untouched and appears in no outbound byte (conformance-asserted). Inspect without modifying: forwarded bytes are byte-identical; redaction applies to the captured copy only. Loopback-only listener, re-checked against what the kernel actually bound. No MITM proxy — no CA that could forge a domain.
What it buys, honestly: detection tiers
TierWhat the org deploysWhat it actually buys
Base ships openbox init --gateway sets the env at user scope Tamper-evident, not tamper-proof. A developer can unset one environment variable; doing so is visible — a session with model turns and no gateway spans is a queryable shape, and openbox doctor reports the exposure at every tier, the healthy one included. Bypass is detected, never prevented.
MDM managed settings + root-owned daemon, optionally egress control Prevention, to the extent the org's MDM provides it. OpenBox ships MDM-pushable artifacts (the recipe) — it never ships MDM tooling. A root-owned config still loses to a shell export; only egress control closes that.
Central not built Nothing new in kind — named only so "we could host it" is not mistaken for "we do".
One deliberate divergence from the hook path
A gated model call is refused when /evaluate is unreachable, regardless of fail_closed — there is no fail-open here and no offline grace (a grace window is a local verdict cache wearing a different name, and those are rejected). The gateway is the stronger enforcement point by owner intent; the accepted cost is that a core outage refuses gated model calls. Ungated calls still forward with no round-trip.
Status — read before relying on it
ADR-0021 is a draft, deliberately: the relay, capture, gate, refusal and account evidence are built and conformance-tested, but the daemon a default install runs today is a pure relay — the CLI does not yet wire the evidence emitter or the evaluator into it, and which calls get gated is an open product decision (~52 model calls were measured per turn window; gating everything is a round-trip per call). Three probe questions bound the whole tier: whether subscription-OAuth traffic follows ANTHROPIC_BASE_URL at all (if not, this covers API-key/console orgs only); the refusal's exact HTTP shape (provisional 403 — a wrong shape reads as transient and Claude Code retries around it; if no shape qualifies, refusal descopes to observe-only); and whether an OAuth credential can be matched to an org (else the account rule is detection-only for OAuth). Also out of scope: Codex (deferred), CI machines, non-Anthropic wire formats — and nothing has run against a live stack.

05 Core concepts
Governance levels
Each install runs at exactly one level and reports which: Observe (telemetry, lineage, cost — never blocks) · Advisory (verdicts recorded and surfaced, never applied) · Enforce (verdicts applied — the default since ADR-0016). Only enforce costs a tool call anything: one round-trip per gated hook.
Enforcement is three switches, not tiers
Local secret redaction (on): Write/Edit bodies scanned before anything leaves the machine. Inline evaluation (on): every gated class asks /evaluate — no local risk triage. Findings (off): async guardrail findings surfaced back into the session. Each is independent.
Approvals are four-eyes
An approver is a separate principal with its own credential: the dashboard, openbox approve, or a bounded autonomous approver (ADR-0012) that decides inside an org envelope, starts in shadow mode, and records every outcome. Approving on the machine that filed the request is refused by default.
Lineage: session → commit → deploy
A git hook stamps each commit with an OpenBox-Session trailer (an inferred claim) and signs an attestation into refs/notes/openbox-attest. The deploy action carries it; core marks a commit verified only when ownership and an accepted attestation both hold.
Posture is evidence
Every session start reports its own effective posture — enforce on/off, fail-open/closed, content capture, who decides — so the control plane can tell a governed machine from an ungoverned one without trusting the endpoint's word. openbox doctor prints the same thing locally with per-value provenance.
Two planes, two URLs
The backend is the control plane (agents, policy, approvals — api.openbox.ai); core is the data plane (where events go — core.openbox.ai). Self-hosting? Set both explicitly at auth time — the control plane cannot tell the CLI where your core is.

06 Setup, step by step
1

Install the engine

One no-cgo static binary: the CLI, the hook engine and the git hook. The installer downloads a prebuilt binary for Linux/macOS (amd64/arm64), verifies its checksum, and puts it on your PATH (~/.local/bin). No Go toolchain needed — unless no prebuilt asset matches, in which case it builds from source with Go 1.23+.

# install curl -fsSL https://raw.githubusercontent.com/OpenBox-AI/openbox-shift-left/main/install.sh | bash openbox version

Windows: build-verified only — compile from source with Go 1.23+; install.sh is bash.

2

Get the right credential

OpenBox has two kinds of key, and this is the step people get wrong. You want the organization key (obx_key_…, dashboard → Organization → API Keys) — and only to register. The agent runtime key (obx_…) is minted by registration, never an input to it. Grant the org key create:agent + read:agent.

export OPENBOX_CONTROL_TOKEN=${OPENBOX_REDACTED_SECRET_ASSIGNMENT} # env only — never a flag, so it can't leak into shell history
3

Authenticate the machine

Interactive; every field prefills with a sensible default, so a first run is mostly pressing Enter. One deliberate exception: the agent id never prefills — leave it blank and a new agent is registered for you. Type an id only to reuse an existing agent (it then asks for that agent's DID and keys, masked as you type).

openbox auth Backend URL (control plane) [https://api.openbox.ai]: Core URL (data plane) [https://core.openbox.ai]: Agent id (blank registers a new agent): ← press Enter ✓ registered agent 4f2a… did:aip:9c1b… ✓ wrote ~/.openbox/.env (api key, signing key — 0600) ✓ wrote ~/.openbox/dev.json (agent id, DID, URLs — no secrets)

Self-hosted? Set both URLs here: openbox auth --backend-url http://localhost:3000 --base-url http://localhost:8086. Setting only one sends events to the hosted core and surfaces later as a confusing 401. For CI, skip auth and export OPENBOX_API_KEY, OPENBOX_AGENT_PRIVATE_KEY, OPENBOX_AGENT_DID, OPENBOX_AGENT_ID — a real env var always wins over the file.

4

Govern a project

Installs the hooks into <project>/.claude/settings.local.json and the plugin bundle into ~/.claude/plugins/openbox-observe. It never touches credentials — missing ones stop it with a pointer back to auth.

cd ~/code/my-project openbox init --provider claude-code # or --provider codex

Two defaults to know before you run it: it governs this directory only (run it once per project; sessions elsewhere produce no events at all), and it enforces — blocking, ask-for-approval and secret redaction on by default, on tool calls and prompts alike.

openbox init --provider claude-code --enforce=false # telemetry without enforcement openbox init --provider claude-code --gateway # also relay model calls through the local gateway — see section 04 openbox init --provider claude-code --scope global # fleet rollout — needs managed settings (admin deploy) openbox init --provider claude-code --dry-run # show the whole plan, touch nothing
5

Verify, then just work

openbox dev verify # ✓ can this machine reach and authenticate to core? openbox doctor # the posture actually in effect, and where each value came from claude # nothing to run, no env vars to keep set

Sessions in governed directories now emit telemetry, commits are stamped for lineage, and gated calls wait for a verdict. Re-run init in a project any time — it replaces its own stale hook entries (and says what it retired), never yours, and a plain re-run never silently downgrades posture.

Codex differences worth knowing up front
Codex asks you to trust new hooks via /hooks before they run · maps approval-required to a plain deny · cannot wake a session (late decisions arrive via the findings channel) · hooks are user-wide only, so --scope local is rejected rather than silently governing everything.

09 Honest limits — what this does not prove
Documented as first-class, not fine print

The project's own position: a governance tool that overstates its guarantees is the failure it exists to prevent. Know these before you rely on it.

  • Your credentials sit in a plaintext file. ~/.openbox/.env is 0600 on macOS/Linux, but anything running as you — including the coding agent under governance — can read the signing key and sign events as you. On Windows 0600 is a no-op. Attestation proves origin-of-config, not tamper-resistance against the developer (ADR-0015).
  • Project scope means partial coverage. A default init governs one directory; sessions anywhere else produce no events at all — so absence of events is not evidence of absence of work. Fleet coverage needs --scope global plus a managed-settings deployment.
  • Enforcement prevents mistakes, not motivated bypass. The hook lives in the developer's own config until managed settings are deployed, and under the default fail_closed:false blocking one hostname disables enforcement for that machine. Orgs that need it to survive an unwilling developer set fail_closed — and accept that an outage then blocks work.
  • Content-based policy sees at most the first 64KB of a body. A rule that would match past that offset does not fire. Local secret detection is exempt — it runs before the cap and sees the whole body.
  • Local secret detection is keyword-driven. A high-entropy value beside an unrecognized key name is invisible to it. That reach is measured by tests rather than assumed.
  • Egress is recorded, not controlled — and the gateway does not change that without MDM. OpenBox does not allow-list the coding tool's traffic. Model calls are seen only with the opt-in gateway installed; its base tier is detection (one unset env var bypasses it, visibly), and the daemon a default install runs today is a pure relay — capture and gating are built and tested but not yet wired into what openbox gateway serves (section 04).
  • Commit attribution is an inferred claim unless your pipeline fetches the signed attestation note (refs/notes/openbox-attest — not fetched by default); then it is cryptographically verified.
  • Windows is build-verified, not runtime-verified, and the newest flows (inline evaluation against a live stack, the setup flow end-to-end) are covered by unit/conformance tests plus hand-driven runs — the mock-free testbed run against a live stack is still pending for them. The docs say so per claim.

openbox doctor first, always: every flag, its value, and whether it came from a default, your config, the environment, or an org mandate.

11 Under the hood (if you'll read or contribute)
Repo shape

A Go 1.23+ workspace of small modules, no cgo (ADR-0011). The standing rule: anything provider-agnostic belongs in adapters/common/; a new table, endpoint or service needs an ADR — the engine was once copy-pasted per adapter and the copies drifted on the enforcement path, so it won't be again.

ModuleWhat it owns
provider/the SPI: Installer (install time) + HookEngine (runtime + capabilities)
adapters/common/hookflow/the engine — spool, enforce cascade, inline evaluation, approval hold, rewake, findings loop
adapters/claude-code/ · adapters/codex/one thin adapter each: native hook shape, mapper, output contract, installer
client/openbox-core client: wire payload, AIP signing, verdict parsing
decision/local secret detection and redaction — the one thing still decided locally
cli/the openbox CLI: auth, init, doctor, dev verify, approve, managed
contracts/dev-event/the normalized event contract + wire mapping + conformance suite
actions/openbox-git-action/commit → deploy lineage for CI
testbed/mock-free end-to-end suite: real headless sessions against a real local stack
