# STORY-E6-S10 — Tier-2 synchronous `/evaluate` escalation for high-risk classes

**Epic:** E6 (enforcement — the Tier-2 tier that closes the §2a policy-only floor for arbitrary execution). **Risk:** high (it puts a synchronous network call on the PreToolUse hot path and can upgrade a T1 allow to a real deny; a bug either wedges a tool call past CC's fail-open timeout, egresses content it should not, or silently fails to govern a high-risk call). **Status target:** review (build + validations + both reviews, pending brian G3 + Sam G_SEC).

## Source
- **Design:** `.fab7/sdlc/design/sidecar-policy-sync.md` §7 (verdict tiering, ratified brian 2026-07-14) + §8 tiering follow-on `E6-S10`: "**Tier-2 sync `/evaluate` escalation for high-risk classes.** After a T1-allow on Bash/MCP, call sync `/evaluate` for the full server verdict; own the timeout in-binary (OD-SYNC-8); E6-S3 fail-open/closed on expiry. Closes the §2a floor for execution. Reuses `/evaluate`. **✅ Unblocked** — CC fails open on hook timeout (verified), so the in-binary budget < hook `timeout` invariant is mandatory; conformance must assert our binary emits the fail-closed deny *before* the hook `timeout` would fire."
- **Design §7 T2:** "synchronous `/evaluate`, high-risk classes ONLY (Bash, MCP execution). Full server verdict. Escalation: T1 local runs first (fast floor); if T1 allows, T2 calls sync `/evaluate` for the authoritative full verdict (policy + guardrail classifiers; drift advisory) before the tool runs. This is how the §2a floor is closed — exactly where arbitrary execution makes it dangerous, and nowhere else. Latency `/evaluate` ≈ 1.6 s (S2). Reuses `/evaluate` — no new core surface."
- **OD-SYNC-8 (hook timeout ownership):** the "5 s kill" is **our own** `timeout: 5` in `plugin/hooks/hooks.json`, and **CC FAILS OPEN on a PreToolUse hook timeout** (verified empirically, CC v2.1.210). LOAD-BEARING CONSEQUENCE: a fail-closed gate must never let CC's timeout fire — our binary MUST enforce a **tighter internal budget** and emit the verdict itself on expiry, returning before the configured hook `timeout`. **Invariant: internal budget < configured hook `timeout`, with margin.**
- **OD-SYNC-9 (RESOLVED, brian 2026-07-14):** accept the full sync `/evaluate` latency for v1 (drift is advisory; Bash/MCP are rare). No core fast-verdict mode.
- **Reused seams:** the `/evaluate` transport (`client.Client.Emit`, SL-3/SL-9, fail-open, returns the rich `Evaluation`); the observe `Mapper` (builds the normalized tool-call event with a deterministic idempotency `event_id`, SL-14); the E6-S3 `applyFailurePolicy` (fail-open/closed on a no-verdict decision) + the E6-S2 `mapVerdict`/`applyDecision` apply cascade — **all unchanged**.

## Cross-repo recon (Explore, `../openbox-temporal-sdk-python`, 2026-07-15)
- **The SDK's pre-execution gate order** (`activity_interceptor.py:227-266`): build event → **await `evaluate_event` (synchronous)** → `enforce_verdict` (raise/terminate) → redact → run activity. E6-S10 ports this order for high-risk classes: obtain the sync verdict, then run the SAME apply cascade, before the tool runs.
- **The SDK has NO risk-class tiering** (recon-confirmed): EVERY activity gets the full synchronous `evaluate_event`; the only skips are coarse (`skip_activity_types`, `send_activity_start_event` global toggle, `enforce_task_queues`) — none risk-based. So **T2's "escalate high-risk classes only" is a deliberate shift-left ADDITION**, not a port — the developer-runtime analog of the SDK's skip lists, justified by design §7 ("a gating hook runs on every tool call; a ~1.6 s wait on every Edit makes the developer remove the hook"). It only ever makes the gate MORE thorough (T2 can upgrade a T1 allow to a deny), never loosens a T1 block.
- **The SDK timeout is a single instance-level `self._timeout`** (`client.py:68/111`, default 30 s from `GovernanceConfig.api_timeout`), applied per-call via httpx; there is no separate short/long per-class timeout. E6-S10 supplies the per-tier budget the SDK lacks — mandated by OD-SYNC-8 (CC fails open on timeout; the SDK's Temporal host does not).
- **The SDK fail behavior** (`_handle_api_error`, `client.py:204-208`): `fail_open` → `None` → proceed; `fail_closed` → synthesized `HALT`. This is exactly the Go `applyFailurePolicy` (E6-S3), which E6-S10 reuses verbatim for a T2 outage.
- **The response shape** (`GovernanceVerdictResponse`, `types.py:127-188`) matches the Go `client.Evaluation` already (verdict/reason/policy_id/guardrails_result/approval_id/constraints) — no client parsing change.

## The design (escalation on the proceed path, in-binary timeout)
In enforce mode, on the PreToolUse gate, AFTER T1 (local sidecar) + `applyFailurePolicy`:
```
if ResolveTier2() && isHighRiskClass(toolName) && !decisionTightens(dec) {
    t2 := escalateTier2(...)                 // sync /evaluate, budget-bounded
    t2.RedactedContent = dec.RedactedContent // carry the LOCAL T1 redaction forward
    dec = applyFailurePolicy(t2, policy)      // fail-open proceed / fail-closed deny on a T2 outage
}
```
- **`isHighRiskClass`** (new, `enforce_tier2.go`): the Bash tool (exact name — arbitrary shell) OR any MCP tool call (`classifyTool` kind == `ToolMCP`). Frequent low-risk classes (Edit/Write/Read) and the other shell-catch-all tools (WebFetch/Task/TodoWrite) are **T1-only** — they never pay the `/evaluate` latency (OD-SYNC-9).
- **`decisionTightens`** (new): whether T1 already yields deny/ask (via the UNCHANGED `mapVerdict`). T2 fires ONLY when T1 would otherwise PROCEED — governance only tightens, so there is nothing for T2 to add to a T1 block, and a fail-closed T1 outage (already a synthesized HALT) short-circuits T2.
- **`escalateTier2`** (new): reuse the observe `Mapper` to build the SAME normalized tool-call event (identical deterministic `event_id` → an **idempotency-ready re-send**, SL-14); resolve full credentials (the first hot-path secret I/O in enforce mode — only for a high-risk class with T2 on, i.e. rarely); build the `/evaluate` client; `Emit` under a `context.WithTimeout(budget)`. Any fault (no creds, client-init, transport/timeout, empty response) degrades to a **fail-open decision** (`tier2FailOpen`) so `applyFailurePolicy` decides.
- **`tier2Decision`**: a real verdict → `FailOpen=false`, `Source="tier2:evaluate"` (so a reachable-core ALLOW is never overridden by fail-closed — the E6-S3 crux); `VerdictUnknown` (Emit folds every transport failure/timeout/empty into this) → a fail-open decision, `Source="tier2:fail-open"`. Mirrors the local Client's `isRealVerdictSource` discipline.

## Timeout ownership (OD-SYNC-8, a CORRECTNESS bound)
- **`ResolveTier2Timeout`** (new): default `defaultTier2Timeout` = **3.5 s** (covers the measured ~1.6 s round-trip + the client's bounded retries), env `OPENBOX_TIER2_TIMEOUT_MS` / config `tier2_timeout_ms`, **clamped to `maxTier2Timeout` = 4 s** (overflow-proof, mirroring the T1 `ResolveEnforceTimeout` clamp).
- **Why 4 s, and why hooks.json is UNCHANGED:** the whole PreToolUse hook (config read + T1 gate + T2 round-trip + apply + audit) must return before CC's PreToolUse `timeout` (which fails OPEN — a CC-layer fail-open that would silently defeat a fail-CLOSED org). The **shipped hook timeout stays 5 s**; a 4 s max T2 budget leaves ~1 s of margin for the T1 gate + apply that bracket the T2 call. So no shipped-plugin change is needed, keeping the blast radius minimal. Live E2E + conformance C15 confirm the fail-closed deny lands well under 5 s.
- **Deviation from OD-SYNC-8's literal "split the `*` PreToolUse matcher into a Bash/MCP block (10 s) + a tight block":** infeasible as written — CC runs ALL matching hook blocks and its matcher is an RE2 regex (no negative lookahead), so a `*` catch-all cannot EXCLUDE Bash/MCP; keeping both blocks would fire the hook twice for Bash (double spool + double enforce). The invariant OD-SYNC-8 actually mandates — **binary-owned internal budget < hook timeout, with margin** — is upheld more robustly by a SINGLE `*` matcher + a per-tier in-binary budget (T1 ≤ ~50 ms, T2 ≤ 4 s, both under the 5 s hook). An org needing a larger T2 budget raises BOTH the hook `timeout` (it owns that value) and `OPENBOX_TIER2_TIMEOUT_MS`, lifting the hard-coded ceiling in lock-step (noted follow-on).

## T2 fidelity is bounded by content posture (INV-2)
The T2 event is the observe Mapper's tool-call event, which carries content only when content capture is on. **As of brian 2026-07-15 content capture is ON by default** (reverses the original metadata-only INV-2/OD4/NFR-1 posture; see `ResolveContentCapture`), so out of the box:
- **Content capture ON (now the default):** T2 sends the content → the server runs the FULL pipeline (policy + Guardrail PII/NSFW + LLamaFirewall drift) → the §2a floor is genuinely closed (the guardrail/drift dims are exactly the model-backed, server-side checks the local T1 floor lacks — OD-SYNC-7).
- **Content capture OFF (explicit opt-out):** T2 obtains the server's verdict on METADATA only; the guardrail/drift classifiers have no content, so T2's value narrows to **server-side POLICY divergence** (a richer / more-current server policy than the local bundle).

NOTE — the shell **command** (Bash) and file **body** are NOT carried on observe/T2 events even with capture on (the Mapper is structurally metadata-only for tool events — SL3-SEC-3); capture governs the **prompt** (UserPromptSubmit) and any content the Mapper attaches. So T2's high-risk (Bash/MCP) escalation egresses tool NAME/kind + permission_mode regardless; the "full floor-closing" gain from content-on is the guardrail/drift classification of the content the Mapper DOES carry. Whether to additionally egress the high-risk command/body to close the command-level floor (a narrow, decoupled egress) remains OD-SYNC-12.

## Config / opt-in (default OFF)
- **`ResolveTier2`** (new): default **FALSE** (opt-in, UNLIKE secret detection) — T2 adds hot-path secret I/O + a network round-trip on high-risk calls, and T1-only enforce ("v1 minus T2", §7 Option C) is a valid honest posture. Config `tier2` (*bool) / env `OPENBOX_TIER2`, env wins; a missing/unreadable config leaves it OFF (fail-safe). Only meaningful in enforce mode. With it off, the enforce path is **byte-identical to E6-S9**.

## Scope boundary (what this story IS and is NOT)
- **IS:** `adapters/claude-code/enforce_tier2.go` (`isHighRiskClass`, `decisionTightens`, `tier2Decision`, `tier2FailOpen`, `escalateTier2`, the tier constants + budget clamp); `ResolveTier2` + `ResolveTier2Timeout` + the two `DevConfig` fields + two env names (`creds.go`); the escalation wiring in `hookrun.go`; unit tests + conformance C12-C17.
- **IS NOT:** the verdict cascade / deny-ask writer (E6-S2, unchanged); the failure policy (E6-S3, unchanged); the local `sidecar.Client`/T1 decision (unchanged); the rego/native evaluator + policy sync (E6-S8, unchanged); Tier-3 findings loop (E6-S11); **NO core/backend/sidecar surface change** (reuses `/evaluate` verbatim); **NO shipped `hooks.json` change** (the 4 s clamp keeps T2 under the existing 5 s hook timeout); widening the high-risk set beyond Bash/MCP (a config/policy question, deferred).

## Acceptance Criteria
1. **AC-1 (escalation closes the floor):** enforce + T2 on, a Bash call that T1 ALLOWS but for which `/evaluate` returns BLOCK → CC `deny` with the T2 policy reason, before the tool runs. *(Live E2E + conformance C12.)*
2. **AC-2 (real allow proceeds):** T1 allow + T2 ALLOW → proceed (empty stdout). *(C13.)*
3. **AC-3 (high-risk only):** with T2 on, a non-high-risk class (Edit) is NOT escalated — `/evaluate` is not called and it proceeds T1-only. *(C14 + live E2E.)*
4. **AC-4 (fail-open/closed on a T2 outage, OD9):** a T2 `/evaluate` outage under fail-open proceeds; under fail-closed denies with the content-free fail-closed reason — and the deny lands well before CC's 5 s hook timeout (OD-SYNC-8). *(C15.)*
5. **AC-5 (opt-in default OFF):** T2 off → a high-risk Bash never calls `/evaluate`; byte-identical to E6-S9 T1-only. *(C16 + live E2E.)*
6. **AC-6 (tighten-only short-circuit):** when T1 already denies a high-risk call, T2 is NOT consulted (governance only tightens). *(C17.)*
7. **AC-7 (INV-2):** the T2 egress posture equals observe (metadata-only unless content capture is on — the Mapper strips content on the `/evaluate` path); the enforcement audit records `source=tier2:*` content-free (no command/reason free-text leak). *(Live E2E audit inspection.)*
8. **AC-8 (INV-1):** the obx_ key/seed resolved on the hot path live only inside the client; the returned Decision carries the verdict alone, never the secret.
9. **AC-9 (INV-3b):** the block is synchronous, pre-execution, and bounded by the in-binary T2 budget; on the apply side any fault degrades to proceed (fail-open).

## Open decisions surfaced (owner: brian)
- **OD-SYNC-8 realization (single matcher + binary-owned budget):** the matcher-split is infeasible under RE2/CC run-all-blocks (above); the equivalent invariant is met with a single `*` matcher + a 4 s T2 clamp under the 5 s hook. **Confirm** this realization + the shipped hook timeout staying 5 s (vs. raising it and lifting the 4 s clamp for a slower-core org).
- **OD-SYNC-12 (NEW) — command/body egress for the T2 floor:** content capture is now ON by default (brian 2026-07-15), so the server's guardrail/drift classifiers run on whatever content the Mapper carries. But the shell command/file body are still NOT carried on observe/T2 events (structural, SL3-SEC-3), so the *command-level* floor is still not closed by T2 alone. Should high-risk T2 escalation additionally egress the command/body (a narrow, decoupled egress) to close it? **Recommend: defer** — the content-on default already closes the guardrail/drift floor for carried content; command-level escalation is a further step. **Confirm.**
- **OD-SYNC-11 (NEW) — T2 delivery vs the observe spool (double-send):** T2 sends the tool-call event synchronously with the SAME deterministic `event_id` + Idempotency-Key as the spooled copy the observe path re-flushes on SessionEnd — **live-verified identical** (`cc-fa3ae38f…`) now that the Mapper clock is pinned per-invocation (G3 MINOR-1 fix). Two sends, one key → they collapse once server-side dedupe lands (SL3-IDEMPOTENCY / EXT-core); until then a transient duplicate identical in kind to the accepted "no dev-event dedupe" gotcha. **Recommend: accept** (reuse-faithful, uses the SL-14 idempotency machinery); the alternative (suppress the spooled copy) needs cross-process coordination and would also drop the E7-S8 duration stash. **Confirm.**
